# 技术实现路径.md
## 1.总体架构
> 分层：手机端业务层 → BLE传输层 → ESP32帧解析层 → LCD渲染层
> 所有业务逻辑、导航数据解析、消息监听全部在手机完成；ESP32只负责解析 JSON 报文 + 绘图输出。

### 手机端：Android / 鸿蒙OS APP
> 鸿蒙兼容Android应用模型；可以采用Android原生开发，鸿蒙直接兼容运行；也可ArkTS鸿蒙原生开发，推荐Android Java/Kotlin开发，生态成熟。

### 1.1 APP模块划分
1. **导航SDK封装模块 nav**
    - 高德AMapNavi / 百度BaiduNavi SDK；
    - 监听导航回调事件 `onNaviInfoUpdate`；
    获取：转向动作、提示文本、剩余转向距离、总里程、剩余距离、ETA、进度百分比；
    获取导航路线polyline中心线经纬度数组，用于缩略图overview坐标转换。
    
    > 注意：SDK不输出道路多边形；手机端仅下发屏幕坐标中心线与参数，路面视觉效果由渲染端统一算法生成（见 1.2）。
2. **传感器模块 sensor**
    - 获取系统 `Rotation‑Vector`旋转矢量传感器，计算航向角 heading(0‑359°，正北为0)；
    - 采样频率：10Hz，与导航帧对齐。
3. **消息监听模块 msg_relay**
    - Android `NotificationListenerService`通知监听服务；获取通知栏消息。
    - 过滤包名：短信包名、微信包名；提取标题、发送人、消息摘要；
    - ⚠️限制：只能读取通知栏弹出消息；微信锁屏通知关闭时拿不到完整消息内容；无法读取历史聊天记录。
4. **BLE通信模块 ble**
    - BLE客户端：扫描、连接ESP32‑S3设备；GATT服务发现；特征值写数据；
    - 上层业务数据交给帧封装器，组装 JSON 报文（msg_type + payload）；
    - 控制发送速率，导航帧5‑10fps；消息事件帧触发即发；避免BLE数据包溢出。
    - 自动重连：BLE 断开回调 → 限频扫描（间隔约 5s）→ 发现目标设备 → 连接 → 协商 MTU → 发现服务 / 订阅 Notify → 恢复发送；全程无用户操作，仅 UI 显示连接状态。
    - MTU 自适应分包：以协商后实际 MTU-3 为单包上限切分（不固定 240），ESP32 侧按 `\n` 重组，不受包长影响。
5. **数据模型 model**
    定义内存模型：NavFrame（导航帧）、MessageFrame（消息通知帧）。
6. **UI模块 ui**
    简单Activity：BLE设备扫描列表、连接状态、导航源切换按钮、消息转发开关。

### 1.2 关键处理：透视道路画面生成（手机端完成）
> 渲染形态以 HTML 模拟器为准：**透视梯形道路**（近宽约150px、远宽约36px、两侧流动白色边界虚线、车道中线虚线），不还原真实路口几何。
> 输入：导航路线中心线 polyline（经纬度点）、导航轨迹航向 heading；
> 手机端逻辑：
1. 取车前局部路线（可视距离内），按"车头朝上"旋转 + 平移，映射为 LCD 320×240 **屏幕像素坐标** centerLine（近处点在前）；
2. 拆分已驶过段 pastCenter 与未驶段 routeCenter，计算车辆位置 pos、右下角小地图 overview/overview_dot；
3. 与 heading、导航文本/统计字段组装 NAV_FRAME JSON 报文（见 ble_protocol.md）下发；
4. 梯形路面、边界/中线虚线等视觉效果由渲染端（HTML 与 ESP32 同一算法）基于 centerLine 本地生成，两端像素对齐；
> 特点：只表达主通行方向，不区分岔路口几何；手机不下发道路多边形，仅下发屏幕坐标折线。

### 1.3 通信协议：JSON 报文（详见 ble_protocol.md）
> 协议以 `docs/develp/ble_protocol.md`（V1.6）为准，本节为要点摘录。

#### GATT 服务定义
- Service UUID：`0000FFB0-0000-1000-8000-00805F9B34FB`
- Write Characteristic UUID：`0000FFB1-0000-1000-8000-00805F9B34FB`：主机→设备，属性 Write Without Response；
- Notify Characteristic UUID：`0000FFB2-0000-1000-8000-00805F9B34FB`：设备→主机，上报 DEV_STATUS / PONG；
- 属性为 Write Without Response，无链路应答；上层以 `\n` 做帧边界。

#### 报文格式
- UTF-8 单行 JSON + `\n` 帧结束符；必含 `msg_type` 字段；帧内不设 CRC（原二进制帧方案已废弃），解析失败由设备计数并经 DEV_STATUS `err` 上报。
- 类型：NAV_FRAME / SET_CONFIG / GET_CONFIG / CLEAR_SCREEN / POPUP_MSG / POPUP_CLOSE / PING / PONG / DEV_STATUS。
- 分包：单包 ≤240 字节（MTU 247，Write Without Response 有效载荷上限 244）；接收端按 `\n` 重组。
- 上限约束：坐标点数 ≤16、单帧 ≤2048 字节、文本长度上限等见 ble_protocol.md §3.1。

### 1.4 手机端数据流
1. 导航运行 → SDK回调拿到导航元数据 + polyline中心线；
2. 传感器读取heading；
3. 手机按 1.2 生成屏幕坐标 centerLine / pastCenter / routeCenter / pos 与 overview；
4. 组装 NAV_FRAME JSON 报文；
5. BLE 写入 Write 特征值（≤240 字节/包，自动分包）发送给 ESP32-S3。
6. 微信/短信通知到来：NotificationListenerService 捕获通知 → 组装 POPUP_MSG JSON 报文 → BLE 发送。

### 1.5 复杂路况模板与主视图透视（B+D 方案）
> 需求：动态表达直道 / 弯道 / 路口 / 环岛等复杂路况，并保证导航路径准确叠加。方案：**模板化路况放大图 + 真实走向**；视觉原型见 nav_sim_v2.html（主视图集成、近大远小投影）与 nav_sim_v3.html（整屏样例）。

1. **模板库（7 类）**：`straight | curve | tjunc | cross | multi | roundabout | fork`，每类含方向/几何参数（见 ble_protocol.md §3.1.1）。
2. **坐标与投影**：手机下发**车头朝上平面像素坐标**；渲染端统一施加主视图"近大远小"投影：消失点 cx=160、深度 y 线性缩放（近端 y=134 全宽 → 远端 y=4 收缩 20%）、路面半宽随深度同步缩放、地面圆投影为椭圆；投影常量两端一致（与行驶条带同一视觉语言）。
3. **路径叠加**：绿路径 = 导航路线在路况段内的真实走向（SDK polyline 抽稀/平滑，环岛含绕行弧），手机端换算为平面折线下发；渲染顺序固定 灰路网 → 亮绿路径 → 车辆光标，路径为准、路网为背景。
4. **触发与切换（手机端）**：`turn_dist` < 200m 且机动非直行 → 附加 road 切换模板放大；驶离恢复行驶条带；帧内无 road 字段即条带模式（向后兼容）。
5. **两端一致性**：模板/投影算法 JS 版（HTML V2 为验收基准）与 C 版 1:1；圆/弧离散为多边形/折线后绘制。
6. **约束更新**：放弃真实路口矢量还原不变；路口段由"统一条带"改为"模板化近似几何放大图"，直行段仍为宽条带。
7. **视觉验收冻结基准（2026-09-02，nav_sim_v2.html V2 迭代）**：模板近端路面基准半宽 main≈62px（主通行近宽≈124px，较初版 +1/3）；道路两侧流动虚线仅绘制在**导航路径所在道路**，其余支路为静态边线；环岛透视呈横椭圆（长轴水平 a≈58 / 垂直半轴 b≈34）；黄车三角较路径起点上移约一个身位；弹窗显示规则见 2.1。

## 2. ESP32‑S3固件实现
ESP‑IDF / Arduino‑S3均可；推荐ESP‑IDF。

模块划分：
1. BLE Server：GATT 服务，FFB0 服务 / FFB1 Write / FFB2 Notify 特征；接收数据放入环形接收 buffer。
2. protocol/frame_parser：从环形缓冲区按 `\n` 切分 JSON 报文；解析失败丢弃并计数（DEV_STATUS `err` 上报）；分发 msg_type。
3. lcd_driver：SPI 2.8寸LCD驱动；基础绘图API：fillRect、drawLine、drawDashedLine、fillPolygon、drawText、drawCircle。
4. render/render_nav：接收 NAV_FRAME，执行整套 UI 渲染：黑底清空、按 centerLine 本地生成并绘制透视梯形道路、流动边界虚线、车道中线虚线、路线、三角光标、提示文字、罗盘、统计信息、右下角 overview。
5. render/render_message：消息帧到达，LCD弹出消息弹窗；设置超时时间，超时后清除弹窗。

> ESP32不做任何坐标计算，所有坐标全部来自手机下发帧，直接送入绘图API。

### 2.1 显示调度与任务模型
- 任务划分：BLE 接收（GATT 回调写入环形缓冲）→ 协议解析任务（按 `\n` 切分 / JSON 解析，失败计数入 DEV_STATUS `err`）→ 显示任务。
- 显示任务：独立定时器 **~30fps** 重绘；维护当前帧缓存（最近 NAV_FRAME 数据 + 弹窗状态 + 信号中断态）；虚线流动 offset 按 `dash_speed` 由显示任务推进，与输入帧率（5-10fps）解耦，动画观感接近 HTML 60fps。
- 渲染状态机：`待机`（黑屏）→ 收到 NAV_FRAME 进入 `导航`；`导航` 态可叠加 `弹窗`（POPUP_MSG，默认 5s 超时自动关）与 `信号中断`（连续 3s 无 NAV_FRAME）提示层；收到 CLEAR_SCREEN 或 BLE 断开回到 `待机`。
- 待机态收到 POPUP_MSG 同样显示弹窗（弹窗层独立于导航层）。
- 弹窗显示规则（V1.6）：内容可视 3 行×17 全角；超长内容首屏多停 3s（约 4.4s）后每 1.4s 逐行上滚、末屏停留 2.4s 自动关闭；弹窗期间非弹窗区域置灰、弹窗文字绿色，关闭恢复。
- 缓冲策略：LCD 控制器自带 GRAM，显示任务仅重绘变化区域（主视图 320×150 与弹窗/提示区），不做全屏整帧搬运；如需平滑可加单帧缓冲（320×240×2B ≈150KB，ESP32-S3 SRAM 可容纳）。

### 2.2 中文字库与字形
- 字库：内置 **GB2312 全 6763 汉字（16×16 点阵）+ ASCII 半角（8×16）**，约 230KB，存 flash（只读资源分区）；`drawText` 支持 UTF-8 解码 → GB2312 索引查表。
- 特殊字形：`↑`（罗盘"↑北"）、`｜`（消息标题分隔）、`…`（截断省略号）等纳入字库或由绘图程序绘制，避免缺字。
- 缺字兜底：GB2312 之外的生僻字显示为占位方块（不崩溃、不计数）。

## 3. Web模拟器
`simulator_web/nav_sim_320x240.html`
- 320×240 Canvas黑底模拟LCD；
- 实现和ESP32完全一致渲染逻辑：宽条带道路模式；
- 可导入/导出协议 JSON 帧，做 PC 端原型验证，调试渲染效果，可用于手机端逻辑调试。

## 4.权限清单 Android APP
需要申请权限：
1. ACCESS_FINE_LOCATION：导航定位、BLE扫描
2. BLUETOOTH、BLUETOOTH_ADMIN、BLUETOOTH_SCAN、BLUETOOTH_CONNECT
3. NotificationListenerService：通知监听权限（系统设置手动开启）
4. READ_SMS：读取短信（可选，如果要短信转发）

> NotificationListenerService属于特殊权限，代码无法自动授予，用户必须跳转到系统设置手动打开。

## 5.高德/百度SDK关键注意点
1. 需要申请对应平台Key；AndroidManifest配置key；
2. 导航SDK必须运行在前台；后台容易被系统杀死；
3. 导航SDK的 `calculateDriveRoute` 静态算路用于规划；`AMapNavi`实例用于实时导航回调。
4. 无法获取道路边界矢量，严格按照方案，手机端基于导航中心线生成**模拟宽条道路矢量**下发。

## 6. 鸿蒙OS适配说明
1. Android APK包可以直接在鸿蒙设备兼容运行；
2. 如果做纯鸿蒙ArkTS版本：使用鸿蒙地图服务；鸿蒙BLE API；鸿蒙通知监听；开发量更大，优先Android方案。

## 7.扩展备选通信：WiFi‑TCP
BLE为主方案；备选ESP32开启TCP Server；手机TCP客户端；同一局域网通信；适合桌面调试；车载移动场景BLE更合适。
